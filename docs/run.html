Before you start

For the Docker routes you need Docker Engine 24 or newer (Docker Desktop on macOS and Windows) with the Compose v2 plugin, plus about 1 GB of free memory.

check
$ docker version --format '{{.Server.Version}}'
$ docker compose version
$ git clone https://github.com/UDogg/DistKV.git && cd DistKV

Ports used by default: 8080 (single-container dashboard), 7001–7005 (nodes), 8090 (historian), 9090 (Prometheus), 3000 (Grafana). Free them or remap them, as described in Troubleshooting.

One container

The image ships the demo supervisor, which starts five distkv processes inside the container, drives traffic at them and serves the dashboard.

  1. Build the image

    Builds every binary and the embedded dashboard. Node.js isn't needed, because the dashboard bundle is committed.

    $ docker build -t distkv:local .

  2. Start the demo

    Overriding the entrypoint selects the demo supervisor. --listen 0.0.0.0:8080 makes the dashboard reachable from outside the container.

    $ docker run --rm -d --name distkv-demo -p 8080:8080 \
    --entrypoint distkv-demo distkv:local \
    --listen 0.0.0.0:8080 --dir /data/demo --historian=false

    The history panel stays off in this route, because the image has no Python. Use the Compose stack or make demo to get the SQLite history.

  3. Open the dashboard

    Go to http://localhost:8080. After about 10 seconds every shard has a leader:

    expected
    HEALTHY   LIVE · SSE   DEMO
throughput  ~800 ops/s     p99  ~3.6 ms     shards 24 / 24     nodes 5 / 5

  4. Crash a node

    Press kill -9 on any node card, or use the control API. Leadership of its shards moves to the survivors within about a second, and the availability tile stays at 100%.

    $ curl -X POST localhost:8080/demo/nodes/n3/kill
$ curl -s localhost:8080/demo/info | grep -o '"failed_total":[0-9]*'
    verified result
    {"node":"n3","status":"ok"}
"failed_total":0          # 9,952 client operations, none failed

  5. Follow the incident

    The kill opens incident #1: a red alert slides in, and a strip above the charts shows its severity, elapsed time and recovery progress. Press 🩹 Heal everything (or H) and a green resolved alert follows once every node and shard is healthy again.

    Open 📄 Report in the Incidents & reports card for the post-incident review: time to recover, client availability, per-shard failover times, charts and a timeline. Download it as HTML or Markdown, or print it to PDF. The Logs card shows each node's own server log next to the dashboard's events.

  6. Stop it

    $ docker stop distkv-demo

Docker Compose stack

Each node runs in its own container with its own volume, as it would on separate machines. A load generator keeps 1,000 ops/s flowing, so every chart has data from the start.

  1. Start everything

    $ docker compose -f deploy/docker-compose.yml up -d --build
# or: make compose-up

  2. Wait for healthy nodes

    Each node container has a health check that passes once every shard it hosts has a leader.

    $ docker compose -f deploy/docker-compose.yml ps
    expected
    distkv1     running   Up 21 seconds (healthy)
distkv2     running   Up 21 seconds (healthy)
…
historian   running   Up 20 seconds
loadgen     running   Up 20 seconds

  3. Open the services

    ServiceURLWhat it shows
    Dashboard + historylocalhost:7001/ui/?historian=…8090Live cluster view, plus the SQLite timeline from the historian
    Node APIlocalhost:7001 – 7005Each node serves the API and the dashboard
    Grafanalocalhost:3000Pre-built “DistKV” dashboard, anonymous admin access
    Prometheuslocalhost:9090Scrapes all five nodes, with SLO alert rules loaded
    Historianlocalhost:8090/statsSample and event counts in its SQLite database

    The dashboard here is read-only. The node containers have no supervisor to restart processes, so the chaos buttons appear only in the single-container and make demo routes. Under Compose, inject failures from the terminal as shown in Break things.

Talk to the cluster

Send requests to any node: if it doesn't lead the key's shard, it forwards the request to the node that does.

curl

$ curl -X PUT 'localhost:7005/v1/kv/user:42?ttl=60s' --data alice
$ curl localhost:7002/v1/kv/user:42
verified result
{ "key": "user:42", "version": 1927, "shard": 4 }
alice

The CLI, inside a container

The images contain distkvctl. They have no shell, so run the binary directly:

$ docker compose -f deploy/docker-compose.yml exec distkv1 \
    distkvctl --endpoints http://localhost:7001 put greeting hello --ttl 10m
$ docker compose -f deploy/docker-compose.yml exec distkv1 \
    distkvctl --endpoints http://localhost:7001 cluster

Clients on your host

Smart clients normally contact shard leaders directly, using the member addresses the cluster reports. Under Compose those are container hostnames such as distkv2, which your host can't resolve. Turn smart routing off so requests go through the published port and the nodes forward them:

ClientSetting
distkvctl, distkv-bench--no-smart
Goclient.Config{DisableSmartRouting: true}
PythonClient("http://localhost:7001", smart=False)
TypeScriptClient.connect({ endpoints, smart: false })

Without this setting, host clients fail with lookup distkv2 … no such host. The single-container route doesn't have this problem, because all of its nodes listen on 127.0.0.1 inside one container.

Break things

Each command below was run against the Compose stack. The status line after each one is what the cluster reported a few seconds later. n3-0 means node n3 is down and leads 0 shards.

FailureCommandObserved
Crash a nodedocker compose -f deploy/docker-compose.yml kill distkv324/24 shards led · n1 8 · n2 6 · n3 down · n4 4 · n5 6
Bring it backdocker compose -f deploy/docker-compose.yml start distkv324/24 · leaders rebalanced to 6 · 5 · 4 · 4 · 5
Partition a nodecurl -X POST localhost:7002/v1/admin/faults -d '{"isolated":true}'24/24 · n2 isolated, leads 0 · others 6 each
Heal itcurl -X POST localhost:7002/v1/admin/faults -d '{}'24/24 · 5 · 4 · 5 · 5 · 5
Packet losscurl -X POST localhost:7004/v1/admin/faults -d '{"drop_percent":30,"delay_ms":5}'24/24 · 0 errors · p99 rises from 2 ms to ~100 ms until healed

The historian logs each change as an event. After the sequence above, it had recorded these:

$ curl -s 'localhost:8090/events?limit=20'
event counts
leader_change 30 · shard_unavailable 5 · shard_recovered 5
node_down 1 · node_up 1 · partitioned 1 · healed 1

Keep one node down at a time. With three replicas, every shard tolerates one failure. A second simultaneous failure leaves some shards without quorum, and the dashboard marks them no quorum until a node returns.

Without Docker

Needs Go 1.24 or newer. Python 3.9+ is optional: if it's present, the history panel runs too. The nodes are real operating-system processes, so kill -9 sends a real SIGKILL.

$ make demo                # dashboard on http://localhost:8080
$ make top                 # optional, Rust terminal monitor (needs cargo)

Prefer the cloud? Open the repository in GitHub Codespaces, wait for the build, then run make demo. Port 8080 opens in your browser automatically.

Troubleshooting

“429 Too Many Requests” while pulling base images

Docker Hub limits anonymous pulls per IP, and shared cloud and CI machines hit the limit often. Sign in with docker login, or pull the same images through Google's public mirror and tag them:

$ docker pull mirror.gcr.io/library/golang:1.24-alpine && docker tag mirror.gcr.io/library/golang:1.24-alpine golang:1.24-alpine
$ docker pull mirror.gcr.io/library/python:3.13-alpine && docker tag mirror.gcr.io/library/python:3.13-alpine python:3.13-alpine
$ docker pull mirror.gcr.io/prom/prometheus:v2.53.0 && docker tag mirror.gcr.io/prom/prometheus:v2.53.0 prom/prometheus:v2.53.0
$ docker pull mirror.gcr.io/grafana/grafana:11.1.0 && docker tag mirror.gcr.io/grafana/grafana:11.1.0 grafana/grafana:11.1.0

Then run docker build or docker compose up again. Docker uses the local tags, so neither command needs Docker Hub.

A port is already in use

Change the host side of a mapping. For the single container, use -p 9080:8080 and open localhost:9080. Under Compose, edit the ports: lines in deploy/docker-compose.yml, for example "17001:7001".

Nodes stay “unhealthy”

A node turns healthy once every shard it hosts has a leader, which takes a majority of the 5 nodes. Check that all node containers are running, then look at a node's logs:

$ docker compose -f deploy/docker-compose.yml logs distkv1 | tail -20

If you changed DISTKV_SHARDS or the member list on an existing cluster, the nodes refuse to start, to protect data placement. Remove the volumes with down -v and start again.

Dashboard shows “Simulation mode” instead of live data

The dashboard falls back to simulation when it can't reach /v1/cluster within 2.5 seconds. Make sure you opened a node's address (:7001/ui/) or the demo's (:8080), and not a file on disk.

Apple Silicon and ARM machines

Nothing special is needed. The image builds natively for your architecture, and released images on GHCR are multi-arch (linux/amd64, linux/arm64).

Clean up

$ docker stop distkv-demo                                  # single container
$ docker compose -f deploy/docker-compose.yml down -v       # Compose, including volumes
$ docker image rm distkv:local

down without -v keeps the node and history volumes. The next up then resumes the same cluster from its write-ahead logs, and the historian's timeline continues where it stopped.
